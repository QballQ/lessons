# SIMS 安全保障模块：面向学校系统管理员的说明文件

> 本文为 `01_Brief_for_IT.md` 的中文译本，供学校系统管理员参考。如中英文版本有出入，以英文版为准。
> Chinese translation of `01_Brief_for_IT.md`. Where the two versions differ, the English version is authoritative.

本文件于2026年10月为常州威雅学校（Wycombe Abbey School Changzhou）编制。读者对象：正在自主开发校内 SIMS（国际学校教务管理系统）的 IT 同事，以及他所使用的编程智能体（DeepSeek、Claw）。

## 1. 执行摘要

学校需要在 SIMS 内部建立一个 CPOMS 式的安全保障记录系统，而不是一个独立的工具。任何教职工都必须能在两分钟之内记录一项关注事项，而该记录随后仅对必要知情的人员可见。本交接包中的模块实现了这一点：

- **复用 SIMS 数据。** 学生、教职工、班级、教室、科目和课表均来自现有的 SIMS 数据表，不复制任何数据。
- **从设计上权限隔离。** 三个访问可见层（ring）：教牧（学生关怀）、安全保障团队、仅限安全保障负责人（DSL）；再加上按单条记录授予的访问授权。SIMS 超级管理员标志不赋予对安全保障记录的任何访问权限。
- **双语。** 每个标签、类别和状态都有英文和中文，沿用 SIMS 已采用的模式（vue-i18n，en 和 zh-cn）。
- **精确定位事件。** 日期和时间、时段或节次、地点（关联到 SIMS 教室）、科目，以及根据学生所在班级自动查出的课表课程。
- **身体图、文件、处理记录、提醒、机构字段。** 与截图中的 CPOMS 表单结构相同。
- **所有操作均被审计**，包括读取。叙述性文本使用不存放在数据库中的密钥进行静态加密。

本交接包包含：一个可运行的 Django 应用（已针对 SIMS 桩模型完成测试）、Vue 3 页面和组件、双语语言文件、初始数据、供编程智能体使用的构建提示词，以及本说明文件。

## 3. 访问模型：权限隔离

### 3.1 角色（保存在安全保障应用中，而非 SIMS 岗位矩阵中）

| 角色 | 人员 | 可见范围 | 可执行操作 |
|---|---|---|---|
| DSL | 安全保障负责人（DSL），如学校选择，也可包括校长 | 全部记录，包括仅限DSL的记录 | 全部操作：更改状态和可见层（ring）、授予和撤销访问授权、管理类别、地点、时段、提醒组和角色、导出、软删除（标记为已删除） |
| DEPUTY | 副负责人（Deputy DSL）及安全保障团队，可选择限定在小学部、中学部或寄宿范围内 | 所在学部内的安全保障团队层和教牧（学生关怀）层记录；仅限DSL的记录不可见，除非被提醒或获得访问授权 | 编辑事实信息、更改状态、将可见层提高至仅限DSL（绝不可降低）、提醒教职工、按单条记录授予访问授权、添加处理条目 |
| PASTORAL | 班主任、年级主任、学院（House）导师，范围限定为班级、年级、学院或某一学部 | 仅限范围内学生的教牧层记录（默认为福利、考勤、医疗类别） | 读取、添加备注、上传文件 |
| 任何在职教职工 | 所有拥有 SIMS 教职工账号的人员 | 本人提交的记录（由 `SG_REPORTER_SEES_OWN` 开关控制） | 记录任何学生的关注事项、在本人提交的条目中添加备注 |
| 被提醒或获得访问授权的人员 | 提醒或限时访问授权中指定的任何教职工 | 仅限该一条记录 | 读取、添加处理条目、上传、提醒其他人员 |
| SIMS SUPER_ADMIN 或 IT 人员 | 未持有安全保障角色 | 无 | 无。已有测试证明这一点。 |

### 3.2 记录的可见层

- 每个类别都带有一个可见层。记录的可见层取其各类别中最严格的一个。同时带有福利和安全保障类别的记录属于安全保障团队层记录。
- 安全保障团队成员可以将记录提高至仅限DSL；只有 DSL 可以降低。两种操作都会在处理记录中留下条目。
- `Allegation against staff`（针对员工的指控）默认为仅限DSL，应保持不变。
- 一次提醒或一项访问授权只向一个人开放一条记录，绝不会开放该学生的其他记录。

### 3.3 数据流向

```
任何教职工 ──► POST /safeguarding/incidents/ ──► Incident（已计算可见层） ──► 向团队 / 提醒组发出提醒
                                                              │
         记录人仅可见本人提交的条目 ◄───────────────────────┤
         DSL 可见全部 ◄─────────────────────────────────────┤
         DEPUTY（按学部）可见 TEAM + PASTORAL 层 ◄──────────┤
         PASTORAL（按范围）可见 PASTORAL 层 ◄───────────────┤
         被提醒 / 获授权人员可见该条记录 ◄──────────────────┘
         每次读取和写入 ──► AccessLog（仅追加，不含叙述文本）
```

`services.py` 中的 `visible_incidents(user)` 这一个函数是唯一的权威来源。所有列表、详情、学生档案页签、附件下载和仪表盘计数都以它为起点。如果新增端点，也必须以它为起点。

### 3.4 IT 能看到什么、不能看到什么

IT 负责管理服务器和数据库。本设计对这种权限所能获取的内容作了限制：

- 叙述性字段（事件经过、处理记录备注、身体图备注）使用保存在环境变量中（而非数据库中）的加密密钥加密。数据库转储只会显示密文。
- 附件存放在 Web 根目录之外，没有公开 URL，只能通过经过权限校验的视图提供。
- 安全保障相关模型未在 Django admin 中注册。
- 安全保障角色持有人的每一次变更都会被记录，并通知所有现任 DSL，因此有人给自己授予角色的行为当天即可被发现。
- 拥有服务器 root 权限的人仍然可以读取密钥。这属于治理层面的控制，而非技术控制：将密钥保存在仅服务账户可读的文件中，限制服务器登录，并每月审查访问日志（AccessLog）。

## 5. 集成点（使其不成为孤立模块）

1. **学生档案页签。** 将 `StudentSafeguardingTab.vue` 嵌入 `StudentProfile.vue`，与家访记录（Contact Records）页签并列。该页签只显示查看者有权看到的内容，并为所有人提供一个“记录关注事项”按钮。
2. **侧边栏菜单。** 在“系统”（System）或“基础”（Basic）分组下增加一个 `Safeguarding 安全保障` 菜单项，仅当 `/safeguarding/me/` 返回角色时才显示。“新增事件”（Add Incident）路由对所有人开放，可从学生档案进入。
3. **路由守卫。** 新增一项 `meta.sgRole` 检查，读取安全保障 store，并且不对 `isAdmin` 做短路处理。详见 `frontend/safeguarding/router/safeguarding.routes.ts`。
4. **`/users/me/`。** 可选：增加一个 `safeguarding` 键来携带角色信息，以便在模块加载之前就能渲染菜单。模块本身也提供 `/safeguarding/me/` 接口。
5. **课表与教室。** 上下文接口读取 SIMS 课表；地点关联到 SIMS 的教室。
6. **考勤与就诊记录。** 后续阶段：在考勤记录或就诊记录上增加一个按钮，打开已预填学生、时间和类别的表单。
7. **审计日志。** 模块维护自己的访问日志（AccessLog）。如果 SIMS 审计日志提供 Python 辅助函数，也请在 `audit.py` 中调用它，使安全事件集中显示在一处。
8. **通知。** `SG_NOTIFY_HOOK` 指向一个发送邮件或 WeCom 消息的函数。提醒也会在应用内的 `/safeguarding/alerts/mine/` 显示。消息携带参考编号和学生信息，绝不包含事件叙述。

## 6. 隐私、安全与合规控制

| 控制措施 | 位置 |
|---|---|
| 字段级静态加密（Fernet，附密钥轮换命令） | `fields.py`、`sg_rotate_keys` |
| 附件私有存储，下载须经权限检查 | `models.py`、`AttachmentDownloadView` |
| 读取审计，而不仅是写入审计 | `audit.py`、每个视图 |
| 杜绝 `Cache-Control` 泄露：每个安全保障响应均设置 `no-store` | `middleware.py` |
| 不做物理删除；软删除（标记为已删除）须填写原因，仅限安全保障负责人（DSL） | `soft-delete` 操作 |
| 上传文件类型与大小限制，并对每个文件计算 SHA-256 | `views.py` |
| 仅限DSL导出，加姓名与时间水印，并记录日志 | `export.py` |
| 列表页与详情页中的隐藏姓名（Hide Names）开关 | `useSafeguarding.ts` store |
| 黑屏（Blank Screen）按钮、闲置锁定 | 规格说明见第 7 节，待构建 |
| 仅可在校园网内或通过 WireGuard 访问 | 现有的托管决定；保持不变 |

合规说明，需与学校法律顾问确认：

- **中国《个人信息保护法》（PIPL）。** 不满 14 周岁未成年人的个人信息属于敏感个人信息：须取得单独同意、严格限定处理目的、按最小必要原则授予访问权限，且数据须留在中国境内。内部托管即可满足数据本地化要求。保留访问日志，作为遵循必要知情原则的证据。
- **英国实践（KCSIE、COBIS 和 BSO 所期望的做法）。** 指定一名 DSL 并设一名副负责人（Deputy DSL），每名儿童一份按时间顺序编排的记录，儿童转校时进行档案转移，并在儿童离校后长期保留（英国通常的做法是将儿童保护档案保留至其 25 周岁生日）。导出端点即为档案转移机制。
- **针对员工的指控**归入专属的仅限DSL类别，使副负责人无法看到涉及同事的关注事项。

## 7. 本文已作规定、由 IT 负责构建的部分（本交接包中未提供代码）

1. **可点击的身体图图形。** 以固定 viewBox 的 SVG 绘制正面和背面轮廓。点击后放置一个带编号的标记，并将 `x` 和 `y` 以相对于图形框的百分比形式存储，同时附带从 i18n 文件的部位列表中选取的部位代码（`area`）。标记以带编号的图钉形式显示，同时也以列表形式列出，每条标记附一条备注。在详情页上为只读。表单目前使用的是数据结构相同的简单列表编辑器，因此该图形可直接替换接入。
2. **黑屏遮罩层。** 由 store 中的 `blank` 标志切换的全窗口中性色遮罩，点击或按键即可关闭。供有人走近工位时使用。
3. **闲置锁定。** 在安全保障页面上，若无任何输入的时间超过 `idle_timeout_minutes`（来自 `/safeguarding/me/`），则显示该遮罩层并调用 SIMS 的退出登录操作。
4. **侧边栏菜单项与角标。** 未读提醒数量来自 `/safeguarding/me/`。
5. **PDF 导出。** 将导出接口返回的 HTML 交由学期报告已在使用的 PDF 渲染器进行渲染。

## 8. 第一版不在范围内的事项

- **AI 类别建议。** 仅当模型运行在学校自有服务器上时方可接受。绝不可将事件文本发送至外部 API。在有本地部署的模型之前，不要加入该按钮。
- **家长或学生访问。** 绝不允许。
- **行为积分集成。** 行为管理是一个独立的系统，可见范围也不同。
- **叙述内容的全文搜索。** 由于内容已加密，无法进行 SQL 搜索；请改为按学生、记录编号、类别、日期、地点和时段进行搜索。

## 9. 验收清单

- [ ] 没有任何安全保障角色的教师可以为任意学生记录关注事项、上传照片、向“安全保障团队”提醒组发送提醒，之后只能看到自己提交的那一条记录。
- [ ] 没有任何安全保障角色的 SIMS 超级管理员看不到任何记录、仪表盘或角色页面（对应测试 `test_sims_superuser_without_role_sees_nothing`）。
- [ ] 权限范围限定为中学部的副负责人（Deputy DSL）无法打开小学部的记录，也无法打开仅限DSL的记录。
- [ ] 拥有教牧（学生关怀）权限的班主任可以看到本班学生的“福利”类记录，但看不到同一名学生的“安全保障”类记录。
- [ ] 向同事发送提醒后，对方仅能打开该条记录；撤销访问授权后，对方立即无法再打开该记录。
- [ ] 安全保障负责人（DSL）可以查看全部记录、降低可见层（ring）、导出带水印的记录，并可注明原因对重复记录执行软删除（标记为已删除）。
- [ ] 访问日志（AccessLog）记录每一次列表查询、查看、下载和导出，包含用户、时间和 IP，且绝不包含任何叙述性正文。
- [ ] 数据库转储中，`safeguarding_incident.body` 字段显示为密文。
- [ ] 学生档案中显示“安全保障”页签，且该页签按查看者的角色控制可见内容。
- [ ] 所有标签均以中英文显示。
- [ ] 对于发生在上课时间的事件，系统通过课表查询自动预填科目和教室。
- [ ] 系统拒绝移除最后一名在任的 DSL。

## 10. 需要学校决定的事项

1. 谁担任安全保障负责人（DSL），谁担任副负责人（Deputy DSL），以及各副负责人分别负责哪些学部。
2. 哪些年级名称计入小学部（`SG_LOWER_SCHOOL_GRADES`）。
3. 用于替换示例 `TimeBand` 数据行的真实作息时间表和寄宿时段。
4. 各提醒组的成员。
5. 记录人在提交后是否可以查看自己提交的记录（默认可以）。
6. 保留期限，以及学生离校时由谁承担导出职责。
7. 是否允许从内部服务器发送邮件或 WeCom 通知。
